# Update Policy

## Вердикт

Автообновления для пользовательской установки выключаем.

Причина простая: если один пользователь случайно обновится, а другой нет, уроки и поддержка начнут расходиться. Нам нужна одна контролируемая версия.

## Как фиксируем версию

Источник правды:

```text
comandos-hermes.lock
```

В нём закреплены:

- версия COMANDOS Workspace;
- источник панели;
- версия Hermes Agent;
- запрет one-click update;
- запрет auto-update timer/cron.

## Workspace

Workspace ставится не как живой git checkout, а как копия/архив без `.git`.

Это даёт три эффекта:

1. кнопка one-click update не должна быть рабочей;
2. пользователь не подтянет случайный `main`;
3. мы можем обновлять систему только через новый lock-файл.

## Hermes Agent

Hermes Agent на первом этапе ставится официальным установщиком, но:

- не запускаем `hermes update`;
- не создаём cron/timer для обновлений;
- фиксируем установленную версию в отчёте;
- перед публичным релизом заменяем установку на pin по tag/commit.

## Правильное обновление в будущем

Обновление должно быть отдельным сценарием:

1. мы проверяем новую версию на своём VPS;
2. обновляем `comandos-hermes.lock`;
3. пишем migration notes;
4. пользователь запускает отдельную команду обновления;
5. перед обновлением делается backup;
6. после обновления запускаются проверки.

## Что нельзя

- Нельзя ставить из `main` без lock.
- Нельзя включать автообновляющие timers.
- Нельзя оставлять пользователю рабочую кнопку update, если она ведёт в upstream.
- Нельзя обновлять Hermes Agent без проверки совместимости с нашей панелью.
