# Telegram-тестирование бота

Этот навык нужен для живой проверки Telegram-бота после подключения базы и workflow.

Он должен:
- сначала проверить, есть ли в корне проекта файл `DANNYE_DLYA_RAZVERTYVANIYA.md`;
- если файл есть, брать оттуда `telegram_sales_bot_token` и прочие данные, если они заполнены;
- до любых Telegram-тестов проверить, что workflow `06_WF_Test` в `n8n` переведен в рабочее состояние;
- если в текущей версии `n8n` нужен `publish`, выполнить `publish`;
- если используется старый режим, включить `Active`;
- поставить зависимости для `Telethon`;
- поднять локальную пользовательскую Telegram-сессию;
- запросить папку с документами компании;
- собрать компактный контекст;
- спросить целевой `@bot_username` или ссылку;
- провести заданное число тестовых диалогов;
- сохранить raw dialog log рядом с клиентским кейсом;
- обязательно собрать normalized summary report по одному из двух режимов:
  - `knowledge_base_test` для ранней проверки базы через `06_WF_Test`;
  - `sales_final_test` для финальной проверки боевых workflow, prompt-ов, routing и handoff.

## Когда использовать

Используйте этот навык, когда нужно:
- проверить, как бот отвечает по базе знаний;
- прогнать 5, 10 или больше тестов;
- проверить слабые места в квалификации, консультации и handoff;
- получить отчет по качеству ответов до продакшна.
- получить summary, на основании которого понятно, что менять перед следующим прогоном.

## Правила

- Не использовать внешние пути из `~/.codex/skills/telegram-sales-tester`.
- Работать только с файлами внутри этого навыка.
- Спрашивать только недостающие данные:
  - папку документов;
  - Telegram-бота `Отдел продаж`;
  - количество тестов;
  - телефон, код и 2FA только если сессии еще нет.
- Перед каждым новым тестовым прогоном очищать рабочие данные прошлого прогона так, чтобы бот видел нового клиента.
- Для очистки оставлять нетронутыми только:
  - `knowledge_rag`;
  - `products_live`.
- Все остальные тестовые таблицы и записи прошлого прогона разрешено очищать перед новым тестом, если это нужно для честного сценария нового клиента.
- После теста всегда сохранять отчет и показывать абсолютный путь к нему.
- После теста всегда сохранять два артефакта:
  - raw dialog report;
  - normalized summary report.
- Raw dialog report без summary не считать завершенным тестом.
- Для раннего теста базы использовать `report_mode = knowledge_base_test`.
- Для финального sales-прогона использовать `report_mode = sales_final_test`.
- Если тестовая среда уже готова, не заставлять пользователя повторять подготовительный шаг.
- Не начинать Telegram-тестирование, если тестовый workflow не активирован или не опубликован.
- После каждого этапа предлагать только один следующий шаг в готовом копируемом `text`-блоке.
