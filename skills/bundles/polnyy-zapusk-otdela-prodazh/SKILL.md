# Полный запуск отдела продаж

Это верхнеуровневый навык-оркестратор.

Он не должен выполнять весь проект как один слепой линейный прогон.
Он должен:
- читать входные данные проекта;
- читать общий контекст внедрения;
- понимать текущее состояние;
- пропускать уже выполненные этапы;
- выбирать следующий релевантный навык;
- предлагать пользователю только один следующий шаг;
- после завершения этапа обновлять общий контекст;
- продолжать вести пользователя дальше по проекту.

## Основные правила

- Локально для агентских задач скачивать не весь репозиторий, а только папку `skills/` и работать из нее.
- Stack-папки не тащить в локальную рабочую директорию без необходимости:
  - `n8n-stack-v2` скачивать только на этапе `n8n`;
  - `supabase-stack` скачивать только на этапе `Supabase`;
  - другие stack-папки скачивать только если до них реально дошел сценарий.
- Не открывать браузер и не искать внешние инструкции по этапам.
- Не использовать интернет как источник шаблонов или порядка действий, если нужные файлы уже есть в локально скачанной `skills/`.
- Сначала искать `DANNYE_DLYA_RAZVERTYVANIYA.md`. Если файла нет, создавать полный канонический шаблон, а не урезанную версию под этап.
- Сразу после этого искать `KONTEXT_VNEDRENIYA_OTDELA_PRODAZH.md`.
- Если файла контекста нет, создать его по шаблону и заполнить начальными значениями.
- Если файлов `DANNYE_DLYA_RAZVERTYVANIYA.md` или `KONTEXT_VNEDRENIYA_OTDELA_PRODAZH.md` нет, копировать шаблоны из `skills/`, а не сочинять их вручную.
- Не спрашивать пользователя повторно то, что уже есть в общем файле данных или в файле контекста.
- Не заставлять пользователя самому выбирать следующий этап, если состояние уже понятно.
- После каждого этапа предлагать только один следующий шаг.
- Следующий шаг всегда выдавать в готовом копируемом `text`-блоке.
- Источник шагов для выдачи пользователю — только `README.md` этого навыка, разделы `Команда 1..12`.
- Следующий шаг брать из соответствующего блока `Команда N` без смыслового сокращения и без перестановки порядка.
- Следующий шаг выбирать по `RHYTHM_VNEDRENIYA_OTDELA_PRODAZH.md`, а не придумывать произвольно.
- Если этап уже завершен, пропускать его и идти дальше.
- Если следующий этап можно начать автоматически без нового ввода от пользователя, прямо предлагать это.
- Нельзя считать этап векторизации готовым только потому, что в проекте есть папка `bd/` или другие чистые документы.
- Если папки `Base/` нет, сначала нужно вести пользователя в создание `Base`, `prepared_docs/` и `vectorized_docs/`.
- После Telegram-тестирования предлагать навык `Сборка брифа`.
- После `brief` предлагать навык `Промпт квалификатора`.
- После промпта квалификатора предлагать навык `Промпт консультанта`.
- Навыки `Сборка брифа`, `Промпт консультанта` и `Промпт квалификатора` обязаны использовать `skills/prompt-architecture/` как canonical standard layer, а не workflow JSON как источник смысла.

## Как он должен думать о проекте

Этот навык должен понимать, что весь проект — это единый контур:
- сначала готовится платформа автоматизации;
- потом подготавливаются и загружаются знания;
- потом собирается боевая логика отдела продаж;
- потом делается живое тестирование;
- потом собирается `brief`;
- потом сначала собирается промпт квалификатора, потом промпт консультанта.
- потом эти prompt-ы вставляются в боевые workflow в живом `n8n`;
- и только после этого делается финальное тестирование отдела продаж.

Каждый из отдельных навыков — это только часть одного большого сценария.



## AmoCRM как расширение отдела продаж

AmoCRM не является обязательной частью базового запуска. Его подключают после того, как базовый отдел продаж уже работает и прошел финальный sales-тест.

Правильная архитектура AmoCRM:
- добавить `07_WF_CRM_Operator`;
- оркестратор вызывает `crm_operator`;
- prompt оркестратора не переписывается по умолчанию;
- поле `reply_to_user` в оркестраторе остается как есть;
- `MCP AmoCRM` не подключается напрямую к оркестратору;
- `05_WF_Human_Handoff_Workflow` отвечает за заметку и задачу;
- `crm_operator` отвечает за поля и стадии AmoCRM;
- квалификатор и консультант не работают с AmoCRM напрямую.

Подробности этапа — в `references/amocrm-crm-operator.md` и `references/amocrm-commands.md`.

## Что обновлять в общем контексте

После каждого завершенного этапа нужно обновлять:
- статус этапа;
- найдена ли инфраструктура;
- что уже подключено;
- какой следующий шаг рекомендован.

## Что должно быть на выходе

- в проекте есть заполненный `DANNYE_DLYA_RAZVERTYVANIYA.md` или хотя бы частично заполненный шаблон;
- в этом файле для Telegram используются два отдельных поля:
  - `telegram_sales_bot_token`;
  - `telegram_error_bot_token`;
- в проекте есть актуальный `KONTEXT_VNEDRENIYA_OTDELA_PRODAZH.md`;
- пользователь в любой момент видит, на каком этапе находится проект;
- после каждого этапа агент сам предлагает следующий релевантный шаг;
- общий сценарий можно вести как непрерывную установку без ручного поиска инструкций;
- финалом сценария являются `brief`, промпт консультанта и промпт квалификатора.
- после генерации prompt-ов сценарий не считается завершенным, пока prompt-ы не вставлены в боевые workflow `03_WF_Qualification` и `04_WF_Consultation`.
- перед финальным тестированием отдела продаж тестовый workflow `06_WF_Test` должен быть выключен или снят с публикации, чтобы не было конфликта тестовых и боевых триггеров.
- `brief` не должен превращаться напрямую в prompt без role skeleton и input profile.
