# AmoCRM и CRM-оператор внутри отдела продаж

Этот этап нужен после того, как базовый отдел продаж уже работает: n8n, Supabase, база знаний, Telegram, квалификатор, консультант, handoff и финальный sales-тест.

Цель этапа — подключить AmoCRM так, чтобы бот:
- понимал воронку клиента;
- знал поля контакта и сделки;
- писал данные в правильные поля;
- двигал сделку по правилам клиента;
- не ломал основную логику отдела продаж.

## Главная архитектура

AmoCRM не должен висеть напрямую на оркестраторе.

Правильная схема:

- `02_Main_Orcestrator` ведет маршрут разговора.
- `03_WF_Qualification` собирает и сохраняет квалификацию в базу.
- `04_WF_Consultation` консультирует и сохраняет consultation summary в базу.
- `05_WF_Human_Handoff_Workflow` создает заметку, задачу и уведомляет менеджера.
- `07_WF_CRM_Operator` обновляет AmoCRM: поля контакта, поля сделки, этап сделки.

Оркестратор вызывает `crm_operator` как отдельный tool workflow после значимого шага.

## Что запрещено

Оркестратору запрещено:
- напрямую вызывать `MCP Amocrm`;
- самому делать `update_contact`;
- самому делать `update_lead`;
- самому выбирать `field_id`;
- самому писать `custom_fields_values`;
- самому создавать заметки и задачи в AmoCRM.

Квалификатору и консультанту запрещено работать с AmoCRM напрямую.

`05_WF_Human_Handoff_Workflow` может создавать заметку и задачу, но не должен решать карту полей и этапы сделки.

## Обязательный workflow

Нужно добавить отдельный workflow:

`07_WF_CRM_Operator`

Минимальная структура:

1. `When Executed by Another Workflow`

Вход:

```json
{
  "lead_id": "number",
  "input": "string"
}
```

2. `Загрузить полный контекст`

Достает из Supabase:
- внутренний lead id;
- `crm_contact_id`;
- `crm_deal_id`;
- имя;
- телефон, если есть;
- `lead_status`;
- `current_route`;
- `handoff_status`;
- `qualification_summary`;
- `consultation_summary`;
- `purchase_purpose`;
- `budget_min`;
- `budget_max`;
- `purchase_timeline`;
- `product_interest`;
- историю последних сообщений.

3. `CRM Operator` AI-узел

К нему подключен `MCP AmoCRM`.

Разрешены только действия:
- `update_contact`;
- `update_lead`.

Если конкретный handoff workflow делает заметку и задачу, то в `07_WF_CRM_Operator` нельзя использовать:
- `create_note`;
- `create_task`;
- `create_lead`.

4. `Парсинг ответа ИИ`

AI часто возвращает JSON строкой в поле `output`. Его нужно распарсить в нормальный JSON.

5. `Записать событие CRM`

Пишет результат в `public.lead_events`.

Колонка payload называется `payload`, а не `payload_json`.

Пример SQL:

```sql
INSERT INTO public.lead_events (
  lead_id,
  event_type,
  event_category,
  workflow_name,
  status,
  payload,
  created_at
)
VALUES (
  {{ $json.internal_lead_id }},
  'crm_sync',
  'crm',
  '07_WF_CRM_Operator',
  '{{ $json.status }}',
  '{{ JSON.stringify($json).replace(/'/g, "''") }}'::jsonb,
  NOW()
);
```

6. `Return` / `Edit Fields`

Возвращает нормальный JSON оркестратору.

Если `Edit Fields` стоит после записи события в базу, нельзя брать `$json.internal_lead_id`, потому что Postgres возвращает только `success: true`.

Нужно брать данные из узла парсинга:

```text
{{ $('Парсинг ответа ИИ').item.json.internal_lead_id }}
```

Или поставить `Edit Fields` сразу после `Парсинг ответа ИИ`.

## Что нужно снять из AmoCRM

Через MCP AmoCRM нужно получить:

- список воронок;
- список стадий выбранной основной воронки;
- список полей контакта;
- список полей сделки, если MCP это умеет;
- список доступных действий MCP.

Если полей сделки через MCP нет, зафиксировать это явно и работать через поля контакта + этап сделки.

## Что записать в DANNYE_DLYA_RAZVERTYVANIYA.md

Нужно добавить или обновить раздел AmoCRM:

- выбранная основная воронка;
- `pipeline_id`;
- стадии с `id`;
- рабочий смысл каждой стадии;
- поля контакта с `id`, названием и типом;
- поля сделки с `id`, названием и типом, если доступны;
- какие поля пишет CRM-оператор;
- какие статусы сделки ставятся при каких условиях;
- какие MCP-действия разрешены;
- какие MCP-действия запрещены.

## Что спросить у пользователя после снятия структуры

Нельзя самому придумывать бизнес-правила движения сделки.

Нужно показать пользователю найденные стадии и спросить:
- когда ставить `Первичный контакт`;
- когда ставить `Переговоры`;
- когда ставить `Принимают решение`;
- когда ставить `Согласование договора`;
- когда можно ставить успешное закрытие;
- когда можно ставить неуспешное закрытие.

Также нужно спросить:
- какие поля обязательны;
- какие поля можно обновлять по ходу диалога;
- какие поля заполнять только на handoff;
- что делать, если данных не хватает.

## Промпты, которые меняются после AmoCRM

После CRM-карты нужно обновить минимум три промпта:

1. `Prompts/prompt_orchestrator_crm_operator.md`

Оркестратор:
- не трогает AmoCRM напрямую;
- вызывает `crm_operator` после значимых шагов;
- вызывает `crm_operator` после handoff;
- не показывает клиенту технические детали CRM.

2. Промпт `CRM Operator`

Он находится в workflow `07_WF_CRM_Operator`, AI-узел `CRM Operator`.

Он должен знать:
- `pipeline_id`;
- stage map;
- field map;
- что брать из базы;
- что можно извлекать из summary и истории;
- что запрещено выдумывать;
- когда возвращать `no_changes`.

3. `Prompts/prompt_qualifier.md`

Квалификатор должен лучше возвращать подтвержденные факты в `state_patch` и summary, но не должен работать с AmoCRM напрямую.

4. `Prompts/prompt_consultant.md`

Консультант должен сохранять полезное consultation summary, чтобы CRM-оператор мог взять оттуда интересующий продукт, рекомендацию и состояние клиента.

5. Handoff prompt в `05_WF_Human_Handoff_Workflow`

Handoff должен создавать заметку и задачу, но не должен отвечать за поля и стадии AmoCRM.

## Тест после сборки

Перед каждым тестом:
- пользователь удаляет тестовые сделки/контакты в AmoCRM, если хочет полностью чистый визуальный прогон;
- агент очищает рабочие таблицы Supabase;
- нельзя трогать `knowledge_rag` и `products_live`.

Проверить:
- новый лид создается как новый;
- `crm_operator` вызывается оркестратором;
- в `lead_events` появляется `crm_sync`;
- поля AmoCRM заполняются;
- сделка двигается на правильный этап;
- handoff создает заметку и задачу;
- оркестратор не вызывает `MCP Amocrm` напрямую.
