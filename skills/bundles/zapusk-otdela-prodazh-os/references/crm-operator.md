# CRM-оператор

CRM-оператор имеет два разных текста.

## 1. Setup-команда

Это команда для агента, который собирает финальный prompt.

Она нужна, чтобы:
- сходить в AmoCRM MCP;
- получить pipelines, statuses, fields, users, task types;
- сохранить snapshot;
- спросить правила у владельца по воронкам, этапам, критериям переходов, задачам и обязательным полям;
- собрать финальный prompt CRM-оператора.

Setup-команду нельзя считать боевым prompt CRM-оператора.

## Рабочий порядок setup-agent-а

1. Создай папку запуска, если её ещё нет.
2. Проверь, что установлен этот skillpack, и открой:
   - `references/crm-operator.md`;
   - `templates/crm_field_gap.template.md`;
   - `templates/amocrm_snapshot.template.json`;
   - `templates/crm_mapping.template.md`;
   - `templates/crm_operator_prompt.example.md`.
3. Подключись к amoCRM MCP только по `x-license-key`, который дал кабинет COMANDOS ОС.
4. Получи snapshot amoCRM:
   - аккаунт;
   - воронки и статусы;
   - поля сделок;
   - поля контактов;
   - поля компаний;
   - пользователей/ответственных;
   - типы задач;
   - обязательные поля;
   - enum-значения.
5. Сохрани сырой снимок в `amocrm_snapshot.json`.
6. Открой `company_brief.md` и `field_plan.md`, если они уже собраны. Если их нет, остановись и попроси сначала собрать brief, модель продажи, стратегию рекомендаций и field plan.
7. Сравни подтвержденный `field_plan.md` с CRM snapshot и заполни `crm_field_gap.md` по шаблону. Поля предлагай не "на всякий случай", а потому что они нужны для квалификации, qualification gate, живой цепочки боль -> процесс -> последствия -> решение, рекомендации, handoff или выбранной стратегии продаж.
8. Если в CRM нет нужных полей, не выдумывай ID. Скажи владельцу, каких полей не хватает, какую сущность выбрать и какой тип поля нужен.
9. Если владелец добавит или изменит поля в amoCRM, сними повторный snapshot и обнови `crm_field_gap.md`. Старый snapshot нельзя использовать для финального prompt-а, если структура CRM изменилась.
10. Спроси владельца, как должны работать стадии. Это обязательный блок, без него финальный prompt CRM-оператора собирать нельзя.
   - Покажи владельцу список pipeline/status из snapshot простыми названиями и ID.
   - Для каждой стадии, которую CRM-оператор может ставить, уточни критерий перехода: какой факт из `crm_operation_input`, `lead_profile`, `facts`, `qualification_gate`, summary, handoff или latest message даёт право перевести сделку.
   - Уточни, какие переходы запрещены или требуют ручного решения.
   - Не придумывай критерии сам. Примеры можно давать только как подсказку: "минимум обязательных фактов собран", "контакт получен", "бюджет подтверждён", "клиент попросил менеджера", "клиент думает", "отказался", "сделка оплачена".
   - Для стадии "консультация" обязательно проверь `qualification_gate`: если required-факты из `field_plan.md` не собраны или не понятна цепочка боли/процесса/последствий, автоматический переход в консультацию запрещен, если владелец не подтвердил исключение.
   - Если владелец не подтвердил критерий для стадии, эта стадия должна остаться в mapping как "не менять автоматически".
   Минимум уточни:
   - новый лид;
   - квалифицированный лид;
   - консультация;
   - передача человеку;
   - думает / отложенный интерес, если такой статус есть в CRM;
   - отказ / нецелевой;
   - закрытие успешно / неуспешно, если эти статусы доступны.
11. Сохрани согласованные правила в `crm_mapping.md`.
12. На основе актуального snapshot, field gap, mapping и примера prompt-а собери `crm_operator_prompt.md`.
13. Верни пользователю:
   - путь к `amocrm_snapshot.json`;
   - путь к `crm_field_gap.md`;
   - путь к `crm_mapping.md`;
   - путь к `crm_operator_prompt.md`;
   - отдельный готовый блок prompt-а для вставки в COMANDOS ОС.

## 2. Финальный prompt CRM-оператора

Это боевой prompt, который вставляется в COMANDOS ОС.

Он должен содержать:
- реальный входной контракт COMANDOS ОС;
- правила поиска дублей;
- правила создания/обновления контакта;
- правила создания/обновления сделки;
- правила переходов по pipeline/status с критериями владельца;
- правила примечаний;
- правила задач;
- точные ID pipeline/status/custom fields/users/task types;
- правила для всех подтвержденных кастомных полей клиента;
- правила для полей, которые нужны из-за выбранной модели продажи и стратегии рекомендаций;
- правила для фактов боли, текущего процесса и последствий, чтобы CRM-карточка объясняла, почему выбрана рекомендация и стадия;
- правила для qualification gate: какие required-факты блокируют `consultation`, где они лежат во входе и что делать, если они пустые;
- правила note fallback для нужных фактов, под которые владелец не стал добавлять поля;
- запрет трогать поля без данных;
- запрет отвечать клиенту напрямую;
- JSON-ответ о результате через `crm_result`.

Используй пример структуры: [templates/crm_operator_prompt.example.md](../templates/crm_operator_prompt.example.md).

## Реальный вход COMANDOS ОС

В финальном prompt-е нельзя придумывать свой контракт вида `lead/contact/next_action`.

CRM-оператор получает от COMANDOS ОС контекст с полями:
- `crm_operation_input`;
- `crm_operation_input.crm_context.crm_deal_id`;
- `crm_operation_input.crm_context.crm_contact_id`;
- `crm_operation_input.lead_profile`;
- `crm_operation_input.facts`;
- `crm_operation_input.facts.qualification_gate` или эквивалентный structured field state, если runtime его передает;
- `latest_message`;
- `dialog_history`;
- `available_mcp_tools`;
- `mcp_tool_results`;
- `mcp_round`;
- `mcp_max_rounds`.

Правило ID:
- `lead_id` - внутренний ID лида COMANDOS;
- `lead_id` нельзя использовать как ID сделки amoCRM;
- ID сделки amoCRM брать из `crm_context.crm_deal_id` или результата MCP;
- ID контакта amoCRM брать из `crm_context.crm_contact_id` или результата MCP.

Правило бюджета:
- бюджет брать из `crm_operation_input.facts.budget`;
- если есть ID сделки amoCRM, обновлять `price` через `update_lead`;
- если текущий `price` пустой, равен `0` или отличается от бюджета во входе, `update_lead.price` обязателен;
- в `updated` писать `lead.price` только после успешного `update_lead`.

Правило названия сделки:
- если название сделки пустое, тестовое, выглядит как `Сделка #...`, содержит старого клиента или не соответствует текущему клиенту/цели, обновлять `name` через `update_lead`;
- в тестовых прогонах добавлять `test_marker` в название, если он есть во входе, чтобы последующая targeted cleanup могла найти сделку по маркеру;
- если сделка уже закрыта и вход не про закрытие/отказ, вернуть `crm_deal_is_closed`, а не писать новые данные в старую закрытую карточку.

Правило MCP-цикла:
- если нужны данные amoCRM, сначала вернуть `tool_calls`;
- после `mcp_tool_results` вернуть финальный `crm_result`;
- не заявлять create/update, если mutating MCP tool не вернулся со status `success`.
- не писать `create_task`, `update_lead`, `create_note` или другое mutating-действие в `actions`, если такого successful tool result не было.

## Что должно быть в финальном prompt-е

- Роль: CRM-оператор обновляет amoCRM и не общается с клиентом.
- Источник данных: `crm_operation_input`, история диалога, summary квалификатора/консультанта.
- Идемпотентность: повторный запуск не создаёт дубли сделок, контактов, задач и примечаний.
- Поиск дублей: по Telegram username/chat id, телефону, email, имени и operation key.
- Правила контакта: когда создавать, когда обновлять, какие поля писать.
- Правила сделки: pipeline/status, критерии переходов, бюджет, название, источник, ответственный.
- Правила кастомных полей: все подтвержденные поля из snapshot/mapping, а неподтвержденные факты писать в note fallback.
- Правила задач: тип, дедлайн, ответственный, текст.
- Правила примечаний: формат, operation key, когда обновлять/не дублировать.
- Правила ошибок: если ID поля/статуса нет в snapshot, вернуть JSON-ошибку и не выполнять опасное действие.
- JSON-ответ: `tool_calls`, затем `crm_result.status`, `entities_found`, `actions`, `updated`, `skipped`, `errors`.

## Файлы результата

Сохраняй:
- `amocrm_snapshot.json`
- `crm_field_gap.md`
- `crm_mapping.md`
- `crm_operator_prompt.md`

## Что нельзя делать

- Не вставлять в prompt access token, refresh token, client secret, connection string и другие секреты.
- Не использовать тестовые pipeline/status/custom field ID из чужой CRM.
- Не оставлять в финальном prompt-е общие слова вместо конкретных ID из текущего snapshot.
- Не поручать CRM-оператору отправлять сообщения клиенту. Ответ клиенту отправляет основной отдел продаж.
- Не менять pipeline/status без подтвержденного критерия из `crm_mapping.md`.
- Не собирать финальный CRM prompt по старому snapshot, если после field gap владелец добавил или изменил поля.
- Не создавать сделку, контакт, задачу или примечание, если не хватает данных для безопасного действия.
- Не писать в `updated` изменения, которые не подтверждены успешным mutating MCP tool.
