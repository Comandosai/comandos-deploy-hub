# Prompt-flow

Цель: собрать prompts для отдела продаж в правильном порядке.

## Порядок

1. Источники и база знаний.
2. Исследование аудитории, болей, конкурентов и рынка.
3. Подтверждение гипотезы владельцем.
4. Brief.
5. Модель продажи, стратегия рекомендаций и план данных для диалога.
6. Prompt квалификатора.
7. Prompt консультанта.
8. CRM-оператор, если amoCRM включена.

Нельзя перескакивать через исследование, подтверждение гипотезы и план данных. Если данных мало или интернет недоступен, зафиксируй ограничение и попроси владельца добить только недостающие вводные.

## Brief

Используй навык `sborka-brifa`.

Brief должен дать:
- что продаем;
- кому продаем;
- какие боли;
- как квалифицируем;
- какие частые вопросы;
- когда звать человека;
- какие факты обязательно собирать у клиента;
- какие ограничения и запреты.

Перед brief прочитай [research-brief-field-plan.md](research-brief-field-plan.md) и собери `audience_research.md`.

Перед генерацией prompt-ов покажи владельцу краткую гипотезу и получи подтверждение:
- что продаем;
- кому продаем;
- какие боли закрываем;
- какая модель продажи;
- какая стратегия рекомендаций;
- какие данные собираем у клиента;
- какие факты являются обязательным минимумом до консультации.
- какой стиль диалога нужен; если владелец не задал стиль, использовать короткий менеджерский стиль без портянок.
- какая цепочка живой квалификации нужна: запрос -> боль -> текущий путь -> последствия -> решение.

## План данных

После brief создай `field_plan.md` по [templates/field_plan.template.md](../templates/field_plan.template.md).

План данных должен перечислить все факты, которые отдел продаж должен собирать:
- что нужно для квалификации;
- что нужно для рекомендации консультанта;
- что нужно для передачи человеку;
- что нужно для полной CRM-карточки;
- что спрашивать нативно, а что брать из Telegram/истории/summary;
- какие факты обязательны, а какие optional.
- какая стратегия рекомендаций подтверждена: флагман, пакет, каталог, подбор по параметрам, диагностика или передача человеку.
- `qualification_gate`: какие required-факты блокируют `consultation`, какие optional можно добрать позже, какие факты можно брать из payload канала/истории/CRM без вопроса.
- `pain_to_solution_chain`: какие боли искать, как выяснять текущий путь заявки/процесса, какие последствия фиксировать и как потом объяснять решение через эту боль.

Этот файл является источником для prompt-а квалификатора, prompt-а консультанта и CRM field gap.

## Стиль по умолчанию

Если владелец не задал особый стиль, prompt должен включать короткий менеджерский стиль:
- 1-2 коротких предложения;
- без длинных объяснений и рекламных абзацев;
- без фраз, которые обесценивают клиента или звучат как анкета;
- сначала признать запрос, потом задать один деловой вопрос;
- вопрос должен быть про боль, текущий путь заявки/процесса, место потери или следующий шаг.

Плохой вопрос:

```text
Хотите, я помогу быстро понять, откуда у вас идут заявки?
```

Почему плохо: клиент обычно сам знает, какие действия сделал и из каких каналов приходят заявки. Такая фраза звучит как искусственный бот.

Хорошие варианты:

```text
Поняла. Как сейчас проходит заявка: откуда приходит, куда должна попасть и на каком шаге чаще всего теряется?
```

```text
Ок, тогда сначала сузим задачу. Где сейчас больше потерь: первый ответ, передача менеджеру, контроль перезвона или CRM?
```

```text
Что из этого первым бьет по деньгам: потеря заявок, медленный ответ, ручное распределение или пустые карточки?
```

## Цепочка живой квалификации

Default-логика диалога:

```text
1. Признать запрос клиента.
2. Найти боль: что мешает, что раздражает, что теряется.
3. Понять текущий путь: откуда начинается процесс и куда должен прийти результат.
4. Зафиксировать последствия: деньги, время, клиенты, контроль, качество, риск.
5. Только после этого объяснять решение через найденную боль.
```

Это не давление на клиента. Это нормальная работа менеджера: сначала понять, что болит, потом показать, как решение закрывает именно это.

Если ниша не про заявки, адаптируй цепочку:
- авто: текущая машина/сценарий поездок -> что не устраивает -> последствия -> подходящая модель;
- недвижимость: цель покупки -> критерии выбора -> риск/доходность -> подходящий объект;
- товары: задача применения -> ограничения -> плохой исход -> подходящая позиция.

## Runtime input для модели

Prompt квалификатора и консультанта должен требовать, чтобы каждый вызов модели получал текущее состояние собранных фактов. Это не должно быть зашито в коде под одного клиента: список полей приходит из `field_plan.md`.

Минимальный вход:

```json
{
  "qualification_gate": {
    "required_for_consultation": ["..."],
    "collected_required": ["..."],
    "missing_required": ["..."],
    "missing_optional": ["..."],
    "gate_passed": false
  },
  "collected_facts": {},
  "empty_facts": []
}
```

Правило:
- если `missing_required` не пустой, модель не ставит `consultation`;
- модель выбирает один самый важный недостающий факт и спрашивает его нативно;
- если факт уже есть в payload канала, истории, CRM или summary, модель использует его и не спрашивает повторно;
- optional-факты не блокируют консультацию, но помогают качеству рекомендации и CRM-карточки.

## Квалификатор

Используй навык `prompt-kvalifikatora`.

Квалификатор собирает факты:
- цель;
- бюджет;
- сроки;
- интерес;
- контакт;
- готовность к консультации;
- признаки передачи человеку.

Список фактов бери из `field_plan.md`, а не из общего шаблона. Если в плане есть отраслевые поля клиента, добавь их в prompt квалификатора с нативными вопросами.

Поведение квалификатора:
- не начинать диалог с анкеты и обязательного представления;
- если клиент уже написал задачу, сначала ответить по сути, потом задать один самый полезный вопрос;
- имя, контакт, бюджет, срок и боль собирать постепенно, когда это нужно для квалификации или передачи заявки;
- не спрашивать повторно то, что уже известно из Telegram, amoCRM, brief или предыдущих сообщений;
- если клиент спрашивает, кто с ним общается, ответить именем агента из настроек;
- если нужно имя, спросить нативно после пользы: "Чтобы я нормально передала заявку, подскажите, как к вам обращаться?";
- если нужен контакт, спросить нативно: "Куда удобнее передать ответ: Telegram, телефон или email?".
- не переводить в `consultation`, пока `qualification_gate.missing_required` не пустой;
- если клиент написал только общий интерес вроде "хочу автоматизировать заявки", оставить статус `qualification` и спросить один недостающий required-факт: сферу бизнеса, источник заявок, текущую боль или желаемый результат - по приоритету из `field_plan.md`;
- для общего интереса не использовать вопрос "откуда у вас идут заявки?" как default. Лучше спросить, как сейчас проходит заявка, куда она должна попасть и где чаще всего теряется;
- использовать номер, Telegram ID, WhatsApp ID, username и источник из channel payload как уже собранные факты, если `field_plan.md` разрешает брать их без вопроса.

При сборке prompt-а используй скелет: [qualifier_prompt.skeleton.md](../templates/qualifier_prompt.skeleton.md).

## Консультант

Используй навык `prompt-konsultanta`.

Консультант:
- отвечает клиенту;
- использует brief и базу знаний;
- не выдумывает факты;
- просит недостающие данные;
- выставляет `needs_crm_update`, если CRM должна обновиться.

Консультант использует `company_brief.md`, `audience_research.md`, `field_plan.md` и найденные RAG-фрагменты. Он не должен заменять исследование общими знаниями модели.
Консультант следует подтвержденной стратегии рекомендаций: если есть флагман, предлагает его как основной маршрут; если каталог или подбор, не пушит случайный продукт, а подбирает по параметрам из `field_plan.md`.

Поведение консультанта:
- не повторять вопросы квалификатора;
- если данных хватает, сначала дать пользу по запросу клиента;
- если данных не хватает для рекомендации, задать один короткий уточняющий вопрос;
- не начинать каждый ответ с представления;
- если клиент спрашивает, кто отвечает, назвать имя агента из настроек;
- если нужно передать заявку человеку, мягко собрать недостающий контакт и не просить то, что уже есть.
- не начинать консультационную рекомендацию, если `qualification_gate.gate_passed=false`, кроме короткой пользы по уже понятному запросу;
- если gate не пройден, дать короткую полезную реакцию и задать один вопрос по `missing_required`;
- ставить `lead_status="consultation"` только когда gate пройден или владелец явно разрешил исключение в `field_plan.md`.
- если gate не пройден из-за текущего процесса, спрашивать про путь заявки/процесса и место потери, а не так, будто клиент не знает свой бизнес.
- когда gate пройден, консультировать через найденную боль: сначала вернуть ситуацию клиента, потом показать механизм решения, потом предложить следующий шаг.

При сборке prompt-а используй скелет: [consultant_prompt.skeleton.md](../templates/consultant_prompt.skeleton.md).
