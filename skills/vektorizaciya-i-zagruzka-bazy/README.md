# Векторизация и загрузка базы

Полный пакет для подготовки базы знаний и товарной таблицы клиента.

Что делает:
- берет сырые документы;
- помогает привести их к рабочей структуре;
- создает `Base`;
- собирает `docs`, `product_memory`, `products_live`;
- отправляет данные в runtime API;
- получает chunks и embeddings;
- записывает знания в `knowledge_rag`;
- записывает товарные строки в `products_live`.
- после каждого этапа сам предлагает следующий шаг и выдает готовый блок команды для копирования.

## Обязательная структура папок

Навык должен вести workspace в трех рабочих зонах:

```text
Base/
  new_files/
  prepared_docs/
  vectorized_docs/
  processed/
  state/
```

Правила:
- все новые сырые файлы сначала кладутся в `new_files/`;
- очищенные и готовые к векторизации файлы лежат в `prepared_docs/`;
- после успешной векторизации и записи в базу эти же файлы переносятся в `vectorized_docs/`;
- уже обработанные файлы должны убираться из `prepared_docs/`, чтобы не было дублей;
- если есть `products_live.tsv`, после успешной записи он тоже переносится в `vectorized_docs/`.
- в `state/` лежат manifest-файлы, чтобы повторный прогон обрабатывал только изменившееся.

## Что входит в пакет

- встроенный `doc-splitter`
- `doc-splitter-launcher`
- `vector-ingestion-launcher`
- `runner/`
- `.env.example`
- `CYBEROP_BOOTSTRAP_SCHEMA.sql`
- install notes для `Antigravity`, `Claude`, `Codex`

## Когда использовать

Использовать, когда нужно:
- быстро подготовить клиентскую базу знаний;
- собрать товарную таблицу;
- загрузить все это в `Supabase`.

## Откуда брать входные данные

По умолчанию навык должен сначала искать в корне проекта файл `DANNYE_DLYA_RAZVERTYVANIYA.md`.

Если файл найден:
- читать оттуда `tenant_id`, доступы к `Supabase` и ключи;
- не спрашивать повторно уже заполненные поля.
- если в процессе был найден или развернут `Supabase`, дописывать туда URL, логин, пароль и DB-параметры.

Если файла нет:
- спрашивать только недостающие данные;
- или предложить создать шаблон такого файла.

## Как агент должен вести пользователя

Агент не должен требовать, чтобы пользователь сам искал следующий шаг.

После каждого этапа агент должен:
- проверить текущее состояние;
- понять, можно ли пропустить часть сценария;
- предложить только один следующий шаг;
- выдать этот шаг в готовом `text`-блоке;
- если документы уже подготовлены, сразу предлагать ingestion;
- если данные уже загружены, предлагать подключение отдела продаж.

## Как работает повторное обновление

Если у пользователя изменились документы или часть товарной таблицы:
- он складывает новые или обновленные исходники в `Base/new_files/`;
- агент заново очищает только актуальные входы и кладет результат в `Base/prepared_docs/`;
- раннер сравнивает документы и товарные строки с manifest-файлами в `Base/state/`;
- в runtime уходят только изменившиеся документы и только изменившиеся товарные строки;
- после успешной записи обработанные файлы уходят в `Base/vectorized_docs/`.

Важно:
- по умолчанию этот режим хорошо работает для обновлений и частичных изменений;
- автоматическое удаление исчезнувших документов или товаров лучше запускать отдельной явной командой.

## Что потребуется

- папка с документами;
- доступ к `Supabase` или к серверу, где он стоит;
- лицензионный ключ `COMANDOS`;
- хост с доступом к `api.comandos.ai`.

## Команда 2. Привести документы в понятную структуру

```text
Возьми все файлы из текущей рабочей папки как есть, без предварительной ручной подготовки.
Создай `Base/new_files` и сложи туда новые сырые файлы.
Сначала наведи обычную понятную структуру документов:
- разложи хаотичные файлы по логическим группам;
- отдели основные документы, продуктовые материалы, отзывы, инструкции и таблицы;
- не используй пока COMANDOS bundle и специальные skills;
- не векторизуй ничего на этом шаге;
- просто подготовь чистую рабочую структуру, с которой будет удобно работать дальше.

После завершения покажи:
- какие папки ты создал;
- какие файлы куда разложил;
- где теперь лежит основная папка с документами для следующего шага.
```

## Команда 3. Разобрать документы и собрать `Base`

```text

Сделай:
- `prepared_docs`
- `product_memory`, если нужно
- `products_live`, если есть реальные factual live rows

Важно:
- не делай `registry_rows`;
- не придумывай отдельную самодельную таблицу;
- если factual live rows есть, сразу создай canonical `products_live`;

- очищенные файлы клади в `prepared_docs/`;
- уже обработанные файлы не возвращай назад в `prepared_docs/`.

После завершения покажи:
- какие файлы созданы в `prepared_docs/`;
- создана ли `products_live`;
- если не создана, коротко объясни почему.
```

- создай и заполни нужный `.env` для runner;

- сразу покажи пользователю URL входа, логин, пароль и DB-параметры;
- запиши эти данные в `DANNYE_DLYA_RAZVERTYVANIYA.md`.

Если для этого нужны логин, пароль, IP или SSH-ключ, запроси у меня только недостающие доступы.

После завершения коротко покажи:

## Команда 5. Запустить ingestion

```text
Используй `vector-ingestion-launcher`.
Возьми prepared-документы из созданного `Base`.
Запусти ingestion flow:
- отправь документы в `commandos-api`;
- получи chunks и embeddings;
- загрузи результат в Supabase.
- после успешной записи перенеси обработанные файлы из `prepared_docs/` в `vectorized_docs/`;
- не оставляй отработанные файлы в `prepared_docs/`.
- сравни документы и товарные строки с manifest-файлами и отправляй только изменившееся.

Если execution-host не может достучаться до `api.comandos.ai`, используй hybrid mode:
- получи JSON с chunks и embeddings на машине с интернетом;
- затем импортируй этот JSON в Supabase.

После завершения покажи:
- сколько документов отправлено;
- сколько чанков получено;
- сколько записей записано в `knowledge_rag`;
- сколько записей записано в `products_live`;
- были ли ошибки.
```

## Команда 6. Проверить результат
